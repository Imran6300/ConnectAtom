  The SEO engine is the catalogue. Products, industries, use cases, problems and cities are
  records in MongoDB. Every public page is a view of one record, or of a valid combination
  of records, so one edit in the admin console updates every page that uses it.

  A combination page is published only when it is a real buying situation and carries enough
  content of its own. Generating every possible combination would create thousands of
  near-duplicate pages, which is the pattern Google's spam policies target. Section 4 sets
  the gates that prevent that.

  Assumptions in this blueprint
         One monorepo with two Next.js apps: web (public site) and console (portal and
         admin, chosen by host), plus shared packages for the database, UI, SEO helpers and
         auth.
         MongoDB Atlas as the single database, Clerk for customer login, Razorpay for billing,
         matching the platform document you already have.
         English first, with Hindi and Telugu versions added only after English pages prove
         they get traffic.
         Hyderabad and Telangana are the first local market, then other Indian cities.


  Site map and URL structure
  The public site has about 20 route patterns, and each pattern maps to one entity type, so
  a new product, industry or city becomes new pages by adding a record, not code.


  URL rules
         One entity, one canonical URL. Lowercase, hyphens, no dates, no trailing slash, no
         indexable query-string variants.
         The path states the relationship. /industries/pharmacy/medical-fridge-monitor
         reads as "this product for this industry", and the breadcrumb mirrors it: Home,
         Industries, Pharmacy, Medical fridge monitor.
         Three path segments at most.
         A slug is fixed once published. If an editor changes it, the old URL gets a permanent
         redirect automatically (stored in a redirects collection, section 6).
         Words in the slug are the words buyers search: cold-room-monitor , not product-1 .

  Rules for the data
         References use ObjectIds. Slugs are copied onto the referencing record only for
         routing and are rewritten by a job when a slug changes.
         Every public record follows the same status flow: draft, review, live, archived. Only
          live records produce pages.
         Indexes: unique slug on every catalogue collection, a unique compound index on
         ( productId , industryId ) and on ( cityId , productId ), and a text index on guides
         and glossary for admin search.
         A record that is archived keeps its URL and redirects to its parent hub, so no link ever
         returns an error.

  Programmatic SEO page system
  The plan is about 465 public pages after 12 months, starting from about 123 at launch. Only
  the 122 combination pages are generated from rules; every other page is written and
  reviewed by a person.


  The rule that keeps it safe
  Google's spam policies define scaled content abuse as many pages generated mainly to
  manipulate rankings, however they are made, and name using generative AI to produce
  many pages without adding value for users. They define doorway abuse as pages created
  to rank for similar queries, and give city-targeted pages that funnel users to one
  destination as an example.

  That is exactly the risk of a catalogue that multiplies 20 products by 30 industries by many
  cities. The answer is not to avoid combination pages. It is to publish a combination only
  when it passes a gate that proves it is a real buying situation with content of its own
  (below). Google publishes no numeric thresholds, so every number in this section is a
  starting value for you to tune, not a Google rule.

  The combination gate
  A pair page is saved as draft until all five checks pass. The gate runs in the admin
  console and stores its result on the record.

     1. Real buying situation. fitScore is 4 or 5, set by you.
     2. Copy that exists nowhere else. At least 250 words in angle , problem and setup
         written for this pair, and no more than 40% word-sequence overlap with any sibling
         page in the same family. Both numbers are starting values.
     3. Data that differs by pair. At least three of: default alert thresholds, report template,
        standard or rule that applies, a typical failure scenario, an example alert message, a
        recommended hardware variant, install notes, a plan recommendation.
     4. Proof. At least one of: a real pilot or customer, a photograph of a real installation, a
        named technical reviewer. Sample data is allowed only if it is labelled as sample.
     5. Links and action. At least three inbound links from content pages (parent hub, sibling
         industries, sibling products), and a call to action specific to the pair.

  A page that fails stays unpublished. It is not published as noindex to "fix later", because a
  page with no value to a user should not exist.


  The city gate
  City pages are the doorway-abuse risk, so they have a stricter gate:

         You can install and support in that city: a named installer partner or your own visit
         schedule, with a stated lead time.
         Local facts that differ by city, such as the summer temperature and humidity range,
         monsoon and power-cut patterns, and delivery and install time.
         At least one local customer, pilot or partner you can name with consent.
         Different content from every other city page, not the same text with the city name
         swapped.

  Generation workflow
     1. You add or approve a fit row in the admin console, with a score and a one-line angle.
     2. The system creates a draft with everything it can pre-fill from the catalogue:
        thresholds, report template, product specs, related links.
     3. You or a writer complete the fields that must be unique. AI drafting is allowed here,
         but a person checks every technical claim.
     4. The gate runs. On a pass the record moves to review, then to live.
     5. Going live creates the pages row, adds the URL to the sitemap, updates internal links
        on related pages, and triggers on-demand revalidation (section 6).
     6. After 28 days the Search Console snapshot is checked. A page not indexed after 60
        days, or with no impressions after 120 days, is improved, merged into its parent with a
        redirect, or retired. Pruning weak pages is part of the system.


  What not to generate
         A page for every industry and city, or every product and city, such as the 20 by 6
         combinations. Only the four hero products get city pages.
         Pages that differ only by a swapped noun or synonym.
         "Best monitor in [city]" pages, or pages for a city you cannot serve.
         Pages for products you do not offer yet.
         Filter, tag and search-result pages as indexable URLs.
         Translations created only by running English pages through a translator. Hindi and
         Telugu versions are written or reviewed by a native speaker and added only for pages
         that already perform in English.

  order, the title pattern, the structured data and the call to action, so quality stays
  consistent as pages multiply.

  Rules that apply to every template
         Title. Unique per page, built by a helper from the record, with an editor override.
         About 60 characters before the | ConnectAtom suffix is a good target. Google may
         rewrite titles it finds unhelpful, so write for the reader first.
         Meta description. 120 to 155 characters, built from the record's summary , naming one
         concrete outcome. Google may replace it with text from the page.
         One H1 that states the page's topic, then headings in order with no skipped levels.
         Above the fold: what it is, who it is for, and one primary action.
         Images: real product and installation photographs, descriptive alt text, width and
         height set, next/image , and the first image only marked as priority.
         Trust signals on every page: a named author or reviewer with a short bio on guides, a
         "Reviewed on" date, real company contact details, sources for any rule or standard

  The alert flow, which is the core promise
     1. A sensor sends a reading to the ingest service.
     2. The service stores it and checks it against the device's rules.
     3. On a breach that lasts longer than the set delay, it opens an alert.
     4. It notifies the first contact by their chosen channel, for example WhatsApp, SMS, a
        call or email.
     5. If nobody acknowledges within the set time, it escalates to the next contact.
     6. When the reading returns to normal, it closes the alert and records who handled it
         and how long it took.
     7. A missing heartbeat from a device raises its own "device offline" alert, because
        silence is also a failure.

  Every step is logged, so a customer or an auditor can see exactly what happened and
  when.

  first rule, add two alert contacts, send a test alert. When all five are done, the account is
  marked active and the customer-success task in the CRM closes. Most churn in
  monitoring products happens in the first month, when the sensor is installed but nobody
  has set up the contacts.


  Plans and limits
  Plans come from the plan and subscription model in the earlier playbook. The portal
  enforces them: the number of devices, the length of data history, the notification
  channels and the number of users. When a limit is hit, show an upgrade prompt rather
  than failing silently.

  Pre-launch checklist
         Every public page returns 200, has one H1, a unique title and description, and a self-
